# Chu-ban — трекер бытовых задач: дизайн

Дата: 2026-09-02
Статус: одобрено пользователем, готово к написанию implementation plan

## Цель и контекст

Личный подарок-проект: удобный, красивый мобильный-first трекер повседневных
(не рабочих) задач для одного конкретного человека. Ключевое требование —
трекер должен быть безопасен для тревожного пользователя: поддерживать, а не
давить виной за пропуски. Второй пользователь — сам автор (тестовый доступ).

Ограничение: у пользователя только российская карта — все выбранные сервисы
работают на бесплатных тарифах без привязки карты (см.
[../../../../README.md](../../../README.md)).

## Стек

- **Frontend**: React + Vite + TypeScript, собирается как PWA
  (`vite-plugin-pwa`: манифест, service worker, офлайн-шелл, иконки).
- **Auth + данные**: Firebase, план Spark (бесплатный, без карты).
  - Firebase Authentication, провайдер Google.
  - Firestore как основная база данных.
- **Push-уведомления**: OneSignal (бесплатный тариф, без карты), Web Push
  через собственный service worker.
- **Доставка уведомлений по расписанию**: GitHub Actions scheduled workflow
  (cron, каждые 10 минут) — без платного бэкенда. Держит секретные ключи
  (Firebase service account, OneSignal REST API key) как GitHub Actions
  secrets, никогда не попадают в клиентский код или публичный репозиторий.
- **Хостинг**: GitHub Pages, деплой через GitHub Actions при пуше в `main`.
- **Репозиторий**: новый публичный GitHub-репозиторий (публичен код, не
  данные пользователя).

## Ограничение доступа

Вход через Google открыт технически любому Google-аккаунту, но:

1. Firestore security rules разрешают чтение/запись только если
   `request.auth.token.email` входит в список `['dashach98@gmail.com',
   'shakov.georgy@gmail.com']`. Это единственный реальный барьер — работает
   полностью на Spark-плане, не требует Blaze/Cloud Functions.
2. Клиент дополнительно проверяет email сразу после входа: если не в
   списке — показывает экран "доступ закрыт" и разлогинивает. Это UX-слой,
   не защита сама по себе.

Каждый пользователь видит только свои задачи (данные партиционированы по
`uid`), партнёры не видят задачи друг друга.

## Модель данных (Firestore)

```
users/{uid}
  spheres/{sphereId}
    name: string
    color: string          // hex, для точек в календаре и меток
    order: number

  tasks/{taskId}
    type: 'task' | 'epic'
    sphereId: string
    title: string
    description?: string
    deadline?: Timestamp
    status: 'open' | 'done'
    parentEpicId?: string   // проставлен у подзадач эпика
    createdAt: Timestamp
    completedAt?: Timestamp

reminders/{reminderId}      // top-level коллекция, читает cron-job
  uid: string
  taskId: string
  fireAt: Timestamp
  sent: boolean
  createdAt: Timestamp
```

`reminders` — top-level коллекция (не подколлекция), чтобы GitHub Actions
job мог одним запросом с индексом по `fireAt` + `sent` находить все
просроченные напоминания всех пользователей разом.

Индекс: составной индекс `sent ASC, fireAt ASC` в Firestore.

## Ключевые сценарии

### Создание задачи / эпика

Форма: сфера (обязательно), название (обязательно), описание (опционально),
дедлайн (опционально). Если задача — эпик, после создания можно добавлять
подзадачи (обычные задачи с `parentEpicId`).

Если указан дедлайн, можно сразу добавить одно или несколько напоминаний:
пресеты (за час / за день / в день дедлайна / за неделю до) или собственная
дата-время. Каждое напоминание создаёт документ в `reminders`.

### Закрытие задачи / эпика

Обычная задача — тумблер "выполнено". Эпик закрывается только вручную
(не автоматически по подзадачам); при закрытии эпика все его подзадачи
каскадно получают `status: 'done'`.

### Просроченные задачи

Не скрываются, не выделяются агрессивным красным. На карточке/в списке —
мягкая, но ясная плашка: **«Дедлайн подошёл. Возьмись за задачу — или
просто передвинь срок, ничего страшного»**, с прямыми действиями
"Выполнить" / "Перенести срок" на самой плашке (без перехода в другое
место).

### Календарь

Месячный вид, дни с дедлайнами отмечены цветными точками по сфере. Тап на
день → список задач этого дня → тап на задачу → карточка задачи (открывается
inline, без необходимости искать задачу заново в другой вкладке).

### Напоминания и push

1. Клиент при первом входе запрашивает разрешение на push, инициализирует
   OneSignal SDK, логинит OneSignal External User ID = Firebase `uid`.
2. При создании/редактировании напоминания клиент пишет документ в
   `reminders` (без прямого вызова OneSignal — ключ туда не попадает).
3. GitHub Actions workflow по расписанию (`*/10 * * * *`):
   - через Firebase Admin SDK (service account из secrets) запрашивает
     `reminders` где `sent == false && fireAt <= now`;
   - для каждого — вызывает OneSignal REST API
     (`include_external_user_ids: [uid]`), текст напоминания берёт из
     связанной задачи (`title`, сфера);
   - помечает `sent: true` после успешной отправки (идемпотентность —
     при сетевой ошибке `sent` остаётся `false`, попадёт в следующий прогон).

### Статистика

Экран/секция со счётчиком выполненных задач за неделю/месяц, разбивкой
выполненного по сферам, и достижениями-милестонами ("закрыто 50 задач",
"первый эпик завершён" и т.п.). Никаких стриков, никакой статистики,
подсвечивающей пропуски или незакрытые задачи негативно.

### Сферы жизни

При первом входе создаётся небольшой базовый набор (Работа, Отношения, Дом,
Путешествия, Здоровье, Личное). Пользователь может переименовывать,
удалять, добавлять свои в любой момент через настройки.

## Обработка ошибок

- Нет сети на клиенте: Firestore SDK работает в офлайн-режиме по умолчанию
  (кэш + очередь записи), UI не блокируется — синхронизация происходит при
  восстановлении сети.
- Email не в списке разрешённых: экран "доступ закрыт" + кнопка "выйти",
  без доступа к данным (защищено правилами Firestore, а не только UI).
- Ошибка отправки push в GitHub Actions job: не критично — `sent` не
  проставляется, повторная попытка через 10 минут на следующем прогоне;
  job логирует ошибку в вывод workflow для последующей диагностики.
- Удаление эпика с подзадачами: подзадачи удаляются каскадно вместе с
  эпиком (простое поведение, без "осиротевших" подзадач).

## Тестирование / QA

Личный проект малого масштаба — полный набор тестов избыточен. Минимум:

- Один unit-тест на чистую функцию расчёта времени напоминания из
  пресета/кастомной даты (нетривиальная логика с датами).
- Один unit-тест на каскадное закрытие эпика (подзадачи → `done`).
- Ручная проверка в браузере (десктоп + мобильная эмуляция) перед
  деплоем: создание сферы/задачи/эпика, закрытие эпика, просрочка задачи,
  календарь, вход с неразрешённого email.
- GitHub Actions workflow проверяется вручную первым ручным запуском
  (`workflow_dispatch`) перед тем, как полагаться на расписание.

## Деплой

1. Vite build → статические файлы в `dist/`.
2. GitHub Actions workflow на push в `main`: build → deploy на GitHub
   Pages (`actions/deploy-pages`).
3. Firebase config (apiKey и т.д.) — это публичные идентификаторы клиента
   (не секреты), безопасны в билде; реальная защита — Firestore rules.
4. Секреты (Firebase service account JSON, OneSignal REST API key) —
   только в GitHub Actions secrets, используются исключительно в
   cron-workflow, никогда не попадают в клиентский бандл.

## Вне рамок (сознательно не делаем)

- Совместные/командные задачи, назначение задач другим людям.
- Оффлайн-конфликты синхронизации между несколькими одновременно активными
  устройствами (Firestore offline-persistence достаточно для одного
  активного устройства за раз).
- Тёмная тема как отдельная настраиваемая опция на первой версии (можно
  добавить позже, если понадобится — не блокирует релиз).
